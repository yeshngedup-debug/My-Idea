## Route

`/founder/browse-projects` — founder-only, read-only ledger of other founders' project briefs. `app/founder/browse-projects/page.tsx` authenticates with Supabase, checks the Neon role, loads all project rows through a shared Neon helper, removes the signed-in founder's own rows, batch-loads the remaining founders' display names, then renders `BrowseProjectsClient`. The client supplies a local status filter, live result count, empty states, and project cards. There are no server actions, route handlers, browser-supplied IDs, or mutations on this route.

## UI/UX findings

- **U1 — HIGH — CONFIRMED — the only interactive control is a runtime no-op.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:71-75,82-110,115-131`; `components/interactive/segmented-control.tsx:37-98`. Static wiring looks correct: clicks call `onChange`, arrow/Home/End call `setStatus`, the count is derived from `filtered`, and buttons expose `aria-pressed`. Runtime after authenticated login at `/founder/browse-projects`: clicking `In progress` and separately pressing `ArrowRight` moved focus, but `aria-pressed` stayed on `All`, the live count stayed `0 projects`, and neither the list nor the empty state changed. Why it matters: this is the route's only filter, so sighted mouse, keyboard, and screen-reader users cannot narrow the ledger; the persistent `aria-pressed="true"` on `All` actively misreports state. Fix: first restore React hydration on this route, then re-drive click and arrow keys and assert `aria-pressed`, count text, and rendered rows all change together. Root cause is **SUSPECTED, not proven**: the browser diagnostic showed the click fired, the button exposed `reactKeys: []`, `reactEls: 2`, and `nextF: 0`, while the CSP header carried a nonce but script tags rendered `nonce=""`; console errors were only Next HMR WebSocket failures. A hand-driven check on `/founder/browse-students` showed the same kind of filter no-op, which supports a shared hydration/CSP problem but is not proof for this route's source. Prior `reports/visual-recheck.md:148` recorded the founder availability filter working, so the current behavior is a regression or an environment-specific failure.
- **U2 — MED — CONFIRMED — duplicated brand in the rendered document title.** Evidence: `app/founder/browse-projects/page.tsx:19` sets `title: 'Browse Projects | Bhutan Tech Connect'`; `app/layout.tsx:15-20` applies `template: '%s | Bhutan Tech Connect'`. Runtime `<title>` was exactly `Browse Projects | Bhutan Tech Connect | Bhutan Tech Connect`. Why it matters: browser tabs, history, and search snippets repeat the brand and weaken an otherwise clear page label. Fix: set route metadata to `title: 'Browse Projects'` (or use the shared metadata builder with a bare page name) so the root template appends the brand once. This is new route-specific evidence for the issue owned by `reports/orchestrator-audit.md:81`.
- **U3 — MED — CONFIRMED — material brief content is hidden with no reachable expansion.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:173-175` applies `line-clamp-2` to the description; `:177-195` renders at most six skills and a bare `+N` badge; no card has a disclosure or link, and `app/founder/projects/[id]/page.tsx:36-39` returns 404 for another founder's project. Why it matters: the description and skills beyond six are the details a founder needs to judge relevance, and this route offers no keyboard- or touch-reachable way to reveal them. The `+N` badge also has no accessible expansion or text such as "more skills". Fix: add a per-card expand control with `aria-expanded` and a stable `aria-controls`, or add a read-only detail route for other founders' briefs; if the badge remains, label it `aria-label={`${count} more skills`}` and make it activate the expansion. `reports/page-audits/admin-projects.md:42` already owns the general line-clamp precedent for titles; this finding is about unreachable description and skill data.
- **U4 — LOW — CONFIRMED — status dot does not encode status.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:167-170` renders the same `bg-amber-300` dot for every status. Why it matters: the text label still conveys the status and the dot is `aria-hidden`, so there is no WCAG color-only failure, but the dot reads as a status cue while carrying no status information. Fix: either remove the dot or map it to the four statuses with a text label and accessible pattern that does not rely only on hue.
- **U5 — LOW — CONFIRMED — work-mode icon is semantically wrong.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:215-222` pairs the label `Work mode` with `CurrencyCircleDollar`, while the value is `On-site` or `Remote`. Why it matters: the icon suggests money next to a location/mode field and adds visual noise; it is `aria-hidden`, so the impact is visual clarity only. Fix: use a location/remote-appropriate icon (for example `MapPin` for on-site and `Globe` for remote) or remove the icon and keep the text label.
- **U6 — LOW — SUSPECTED — date-only deadlines may shift by timezone.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:47-55,224-231` formats `deadline` with `new Date(value).toLocaleDateString('en-GB', ...)`; `neon/schema.sql:32` defines `deadline` as `date`. Why it matters: JavaScript parses a bare `YYYY-MM-DD` as UTC midnight, so a browser in a UTC-negative timezone can display the day before the stored deadline. Bhutan's UTC+6 is not affected, but remote users could be. Fix: parse date-only strings as local calendar dates or format with an explicit `Asia/Thimphu` time zone; add a regression test for `2026-12-24` in UTC-6 and UTC+6. Marked suspected because runtime seed data did not expose an off-by-one and this route's `Apply by` value was not exercised with an expired or boundary date. Overlaps `reports/page-audits/founder-overview.md:156` and `reports/page-audits/student-overview.md:95-103`.

## Workflow findings

- **W1 — MED — CONFIRMED — transient role-lookup failure sends a founder to the wrong dashboard.** Evidence: `proxy.ts:27-33` catches any `getProfileRole` error and returns `null`; `:123-131` then maps `null` to `ROLE_HOME.student` (`/student`) and permits the visitor to remain there. This gate runs before `app/founder/browse-projects/page.tsx:29-30`. Why it matters: if Neon is briefly unavailable during route protection, a founder trying to browse projects is bounced out of the founder area rather than shown a retry state. This is not data exposure; it is a fail-open navigation fallback. Fix: distinguish "role lookup failed" from "no role" and return a retryable error response for infrastructure failures instead of defaulting to `student`. This is an inherited cross-route issue; reference `reports/page-audits/admin-overview.md:64`, `reports/page-audits/admin-projects.md:82-86`, `reports/page-audits/student-overview.md:156-171`, and `reports/page-audits/founder-overview.md:167`.
- **W2 — LOW — CONFIRMED — the ledger is intentionally a dead end.** Evidence: `app/founder/browse-projects/browse-projects-client.tsx:235-237` says "Read-only brief. Applicants are managed by the founder who posted it."; card titles at `:153-155` are plain `h2` text, not links; no action exists on the card; the only founder project detail route rejects non-owners at `app/founder/projects/[id]/page.tsx:36-39`. Why it matters: after filtering, a founder can only read the short card. If this page is meant to be an inspiration ledger, the copy is honest and no fix is required; if it is meant to start a collaboration, the workflow stops. Fix: decide the product intent explicitly. Either keep the read-only note and document the scope, or add a read-only other-founder detail/intro action with its own authorization and no applicant data.

## Database/RLS findings

- **D1 — MED — CONFIRMED — authorization is page-level only; Neon has no RLS.** Evidence: `lib/neon-data.ts:1-7` states "there is no RLS on the Neon side" and that authorization is enforced in application code; `neon/schema.sql:1-4` likewise creates no RLS policies. `app/founder/browse-projects/page.tsx:22-35` performs the only relevant checks, using Supabase `getUser()` and a Neon role lookup, then passes the signed-in `user.id` into the in-memory own-project filter. The legacy `supabase/schema.sql:78-82` policies are not active on this data path. Why it matters: cross-founder visibility is intentional here, but the unscoped helper `listAllProjectsWithDetails()` at `lib/neon-data.ts:322-332` is shared with admin/student callers, so a future call site that omits a role guard would expose platform-wide rows with no database backstop. Fix: add an explicit read-only, role-aware Neon helper for this route (for example `listProjectsExceptFounder(founderId)`), and/or add defense-in-depth database policy or a server-side `requireRole('founder')` assertion in shared aggregates. This extends `reports/page-audits/admin-overview.md:76` and `reports/FINAL-AUDIT.md:59-60`; it is not a new RLS defect unique to `/founder/browse-projects`.
- **D2 — LOW — CONFIRMED — all project rows and columns are fetched, then narrowed in memory.** Evidence: `app/founder/browse-projects/page.tsx:32-35` calls `listAllProjectsWithDetails()` and filters `row.founder_id !== user.id` after the query; `lib/neon-data.ts:322-332` runs `select * from public.projects order by created_at desc`, and `:191-208` materializes fields this route never sends, including `student_id` and the legacy `budget`. Why it matters: the server transfers and maps rows the viewer cannot use, and a full-table sort grows with platform size even though `neon/schema.sql:87` indexes `(founder_id, created_at desc)` rather than `created_at` alone. This route is not currently an N+1: `:34-35` deduplicates founder IDs and `lib/neon-data.ts:74-87` fetches all names in one `id = any(...)` query. Fix: add a bounded projection with `where founder_id <> ${user.id}`, select only displayed columns, and keep `order by created_at desc`; add a matching index only if measured query plans justify it.
- **Verified clear, not findings:** no server action, route handler, `fetch`, mutation, or URL/body input exists in the route; no browser-supplied founder ID or project ID reaches SQL, so there is no IDOR surface here. SQL parameters are used for user ID and profile IDs at `app/founder/browse-projects/page.tsx:29,35` via `lib/neon-data.ts:47-55,74-87`. Role and project failures throw `NeonDataError` (`lib/neon-data.ts:52-54,84-86,329-331`) and reach the generic retry boundary at `app/error.tsx:18-55`, which does not leak database details. Profile names fall back to `Founder` at `app/founder/browse-projects/page.tsx:40`, and the count/empty states are derived from server data at `browse-projects-client.tsx:124-146`.

## Recommended fixes

1. **U1:** restore and verify hydration on this route before changing filter logic; re-drive click, `ArrowRight`, `Home`, and `End`, asserting `aria-pressed`, count text, and rendered rows change together. Investigate the nonce/CSP and `__next_f` diagnostics as the suspected shared cause, but do not treat them as proven.

3. **U3:** add an expandable card detail or read-only detail route so the full description and all skills are reachable; give the `+N` badge an explicit accessible label and action.
4. **W1 / D1:** make infrastructure failures distinct from missing roles in `proxy.ts:27-33,123-131`, and give this route an explicitly role-aware, bounded Neon projection rather than relying only on the page-level filter.
5. **D2:** replace `select *` with a projected query that excludes the signed-in founder in SQL and maps only displayed fields.
6. **U4 / U5 / U6 / W2:** remove or status-map the amber dot, correct or remove the work-mode icon, format date-only deadlines in a fixed time zone, and decide whether the read-only ledger should stay a dead end or gain a safe next step.
